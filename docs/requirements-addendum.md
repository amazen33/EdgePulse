# Requirements addendum — tenant administration and configurable integration

Status: proposed implementation requirements accepted for roadmap planning; no implemented capability or verified TB feature parity is implied.

## Interfaces and migration sequence

REST over HTTPS is the frontend default through APISIX/BFF. Use gRPC for synchronous calls between separately deployed services, in-process interfaces for modular-monolith modules, Kafka for asynchronous domain events, and MQTT for devices. Use one authorized multiplexed WebSocket connection per browser for updates.

Keep Migration Studio foundation in M1 and configurable connectors/shadow-parity tooling in M3. Make full production legacy import, reconciliation, approval, and cutover the final stage M9, after M8 Deployment Studio. Earlier stages use synthetic inputs or explicitly approved limited samples/shadow reads only. Configuration covers supported source schemas, hierarchy depths, field mappings, units, timestamps, relationships, and sandboxed supported transformations; unknown protocols/custom executable rules can require reviewed adapters. Version, validate, preview, approve, and roll back configurations. M9 requires scoped inventory coverage, counts/hashes and semantic reconciliation, delta catch-up, preserved rule/report parity, rollback rehearsal, acceptance, and authorized cutover. Never automatically import secrets.

Migration Studio also configures and audits change-data capture (CDC) for latest legacy data: approved source/table/tenant scope, a consistent snapshot and stream position, versioned transformations, vault-backed connector access, idempotent apply/checkpoint, lag and source-health monitoring, pause/recovery, and per-tenant reconciliation evidence. PostgreSQL logical decoding is a candidate only after source-version, permissions, key and WAL-capacity checks; ThingsBoard CE configuration and Mosquitto traffic require separately verified capture paths. Before M9, approved limited CDC feeds an isolated shadow read model only. M9 applies the full snapshot and changes to operational owners after a human go/no-go gate. Each migrated rule-chain instance and node must map to exactly one target `tenant_id`; missing ownership, cross-tenant references or unreviewed executable code block activation. Preserve per-tenant rule-graph versions, golden parity, approval and rollback evidence. See `docs/legacy-migration-execution-plan.md` and `docs/adr/XXXX-proposed-migration-studio-cdc-and-tenant-rules.md`.

Use approved, read-only analysis of the actual legacy PostgreSQL schema and data to establish table relationships, tenant/device ownership, data-quality measures and a versioned source-to-target mapping. Compare the migrated data at the same snapshot/CDC position, including relationships, historical aggregates and latest values. Separately prove TB CE rule/alarm behavior and the values shown by dashboards and reports for fixed tenant, role, filter and time-window cases. Record approved conversion/display tolerances and owner sign-off; unexplained differences block M9 cutover even when row counts match. Live-source query load and access require source-owner/DBA approval; no unrestricted Studio SQL or early production import.

Migration Studio reconciliation tests must be filterable by tenant ID or resolved tenant name, mapped legacy/target device ID, and UTC time period, with combinable filters and repeatable evidence. Reject ambiguous names and cross-tenant device selections; use the same event-time boundaries and snapshot/CDC watermark on both systems. Show counts, differences and coverage per selection, but require full approved-scope coverage before M9 acceptance; a filtered passing sample is not a migration completion claim.

IOT-EE operational workflows, service data models and persistence SQL are independent of legacy-system queries. Legacy SQL is used only by approved migration profiling/reconciliation, except that legacy **report** queries and outputs may be retained as versioned compatibility references. Reuse or translate report queries only in the reporting adapter against certified IOT-EE-owned read models, with tenant isolation and output-parity tests. Production services and reports must not depend on the live legacy PostgreSQL database.

## Consoles and identity

Provide system-admin, tenant-admin, and tenant-operator experiences. Inventory the actual legacy TB CE version and workflows before approving a feature-parity matrix; do not infer parity from screenshots or equate operator roles with TB customer users.

Provide a tenant-scoped device map using the device/asset hierarchy and effective per-device permissions. Distinguish fixed installation coordinates from mobile reported positions; carry source, observation time, accuracy and stale/unknown state. REST returns an authorized viewport snapshot, then versioned deltas update visible markers. The existing multiplexed WebSocket is the full-console default; a read-only SSE feed is permitted for a map-only client instead of opening a second WebSocket. Reauthorize and resnapshot on reconnect or scope change. Use PostGIS behind a replaceable spatial adapter when indexed proximity/geofence queries are needed, and a replaceable map renderer and deployment-approved tile source. See `docs/adr/XXXX-proposed-tenant-device-map-and-location.md`.

Tenant-admin scope includes authorized device/asset/profile and relationship management, dashboards, telemetry/history, alarms, rules, reports, operators, and firmware when enabled. Preserve valuable existing rules through compatibility integration.

Keep tenant-scoped document collaboration as an optional, replaceable capability for manuals, work-order attachments and technician file exchange. Evaluate Nextcloud, ownCloud Infinite Scale and alternatives such as Seafile, Pydio Cells and CryptPad against the specific workflow; no provider is selected. The work-order service owns attachment metadata and access policy. A collaboration provider is not the immutable evidence store, firmware binary path or device telemetry store. Verify the exact edition/build license, tenant isolation, OIDC integration, revocation, audit, backup/restore and 24/7 support model before approval. See `docs/adr/XXXX-proposed-kubernetes-options-and-platform-tool-roles.md`.

Admin and operator authentication must have separate login entry points, OIDC clients/audiences, session cookies and authorization policies. A shared identity provider is permitted; separate realms/issuers are configurable for stronger organizational separation. Operator tokens must be rejected by admin APIs. Use authorization code with PKCE, secure HttpOnly cookies for BFF sessions, CSRF protection, short session/token lifetimes, MFA for administrators, and step-up authentication for sensitive operations. Validate issuer/audience and tenant membership server-side; never trust tenant headers alone. Account disabling and grant revocation must invalidate active device access. System-admin access is separately privileged and audited.

Use OIDC authorization code with PKCE and JWT access tokens with server-side issuer, audience, signature, expiry and tenant checks. Refresh tokens remain server-side behind the BFF session; the identity provider owns refresh-token rotation and reuse detection, and the BFF invalidates its session when refresh fails or reuse is detected. Require TOTP authenticator-app MFA for system and tenant administrators; allow phishing-resistant WebAuthn/passkeys as a stronger supported factor. Do not use SMS/email OTP as the privileged default. Operators follow tenant policy, with step-up MFA for sensitive actions. These are recommended defaults pending identity-provider conformance and recovery-flow design.

Authorization combines role/permission rules (RBAC) with resource and request attributes (ABAC), including tenant, hierarchy, environment, resource ownership and action. Deny by default; explicit deny takes precedence; delegation cannot exceed the grantor's effective permissions. Initially evaluate policy through framework-free Java policy interfaces and versioned policy data in the owning service. Keep the evaluator behind a port so a dedicated policy engine such as OPA can be evaluated later without leaking its SDK/model into domain code. Policy authorship and approval are system-admin controlled for platform policy; tenant admins may manage only bounded tenant role assignments and scopes.

Technology and tool replaceability is mandatory: domain/application logic uses owned contracts and ports, never vendor runtime APIs directly. Each selected adapter must pass shared behavioral and operational conformance before it is supported; an alternative is not presumed drop-in. Each service owns its published, versioned provider API contracts and its consumer-side ports/client contracts for dependencies. REST/HTTPS is the frontend and external API default; gRPC is the default synchronous service-to-service transport; Kafka carries asynchronous domain facts. A service exposes only transports needed by its authorized consumers. No service reads another service's database. See `docs/adr/XXXX-proposed-service-api-and-payment-provider-boundaries.md`.

Define a dependency-by-dependency resilience contract before implementing each remote call or long-running workflow: end-to-end deadline, safe retry owner and budget, idempotency/reconciliation, circuit-breaker and bulkhead applicability, bounded queue/backpressure, truthful fallback, observability and operator recovery. Isolate optional AI/report/map/payment load from critical telemetry, alarms and commands. Use Saga-style durable coordination only where a business outcome crosses service owners; do not claim automatic compensation for irreversible device actions. A proposed pre-TB CE anomaly detector may alert and start a human task; only specifically approved high-impact event classes enter a bounded review hold, with explicit disposition and preserved raw events. Flowable Open Source is the provisional human-workflow pilot; CIB seven, EximeeBPMS and FINOS Fluxnova remain candidates. Implement relevant controls with each service and validate cross-system resilience in M6. See the proposed resilience, workflow-selection and pre-TB CE anomaly-review ADRs.

Install an open-source service-topology view in the independently validated observability layer before service instrumentation: Grafana/Tempo Service Graph backed by bounded-cardinality metrics in Mimir. Prove a synthetic service edge and failure/recovery behavior before relying on live application traces. Hubble is the network-flow view if Cilium is selected; Kiali is conditional on Istio Ambient. Neither replaces the application trace graph, tenant-authorized device map or physical infrastructure inventory. See `docs/adr/XXXX-proposed-observability-installation-sequence.md` and the proposed Cilium/Ambient ADR.

Keep RKE2 as the current on-prem lab target; allow a separately built and tested OKD open-source deployment profile and an explicitly approved commercial OpenShift profile. A topology viewer does not require changing Kubernetes distributions. Every service must authenticate callers and authorize tenant/resource actions itself; Keycloak provides OIDC; the proposed Cilium/Istio Ambient profile separates pod reachability from workload mTLS and service policy; OpenBao/Vault provides scoped secrets; OPA may evaluate policy through a replaceable port. None replaces the service enforcement point. Cilium's current mutual authentication is beta and does not satisfy the production workload-authentication gate by selection alone. Falco detects runtime threats, Trivy scans supply-chain artifacts, and SonarQube Community Build is optional code-quality analysis. Ceph RGW remains an unproven on-prem WORM candidate while archived MinIO is rejected as a new default; Apache Iceberg and Spark are optional analytics components outside the operational IoT path. See `docs/adr/XXXX-proposed-kubernetes-options-and-platform-tool-roles.md` and the proposed Cilium/Ambient ADR.

Payments are a replaceable bounded context: consumers call the payments service API, which delegates through a provider-neutral outbound port to isolated provider adapters. Stripe may be first; no provider SDK types leak into service contracts or core code. Usage-based billing consumes finalized usage events; telemetry, alarms and device commands never synchronously depend on payment availability. Prefer hosted checkout/tokenization and never store raw card data. Provider order, PCI boundary, currencies and tax/invoicing ownership require a business/security review before M7 implementation.

Config Studio is backend-first and distinct from Migration Studio and Deployment Studio. It governs typed, versioned platform/service and tenant configuration through validate, preview, approve, apply and supported rollback APIs. Device desired properties remain with device management; source mappings and cutover remain with Migration Studio; infrastructure profiles and IaC plans remain with Deployment Studio. See `docs/adr/XXXX-proposed-config-studio.md`.

AI provider SDKs, including Spring AI integrations, stay in outbound adapters behind Java-owned ports. Provider selection and residency/retention rules are profile-aware. Initial AI features are read-only and fail independently of core IoT operations. MQTT is the initial device transport; legacy protocols require inventory and tested adapters before support is claimed. ThingsBoard CE must be both replaceable through a conforming adapter and upgradeable through a versioned adapter/customization path, with behavioral contract tests and migration evidence. See `docs/adr/XXXX-proposed-ai-and-device-adapter-boundaries.md`.

## Tenant operators and secure device property updates

Add an Operators page: invite/activate, assign roles, scope hierarchy/device access, allowlist writable properties/actions, set access expiration, suspend/revoke, review sessions and redacted activity. Invitations are single-use and expiring. Tenant admins cannot grant beyond their authority; no self-escalation or cross-tenant delegation. Expose effective permissions before saving.

Use a server-mediated device command service rather than direct browser device credentials, raw broker access, or unrestricted network tunnels. Browser REST requests pass tenant/device/action/property authorization, schema/range validation, optimistic concurrency, rate limits, and idempotency checks. Use authenticated TLS device transport (mTLS where supported) and per-device broker ACLs. Persist desired versus reported properties with versioned command IDs, TTL, pending/acknowledged/failed/expired status, and device acknowledgments. An accepted command is not proof the device applied it. Bound offline queues; expire stale commands; reconcile reconnects; prevent replay. WebSockets expose scoped progress only. Firmware, credentials, network routing, and other high-impact settings require distinct privileges and policy-driven approval/step-up. Secrets use vault-backed operations, never generic property reads or event payloads.

## Firmware entitlement

System admins enable or revoke a tenant firmware-management entitlement independently of optional billing. Backend policy requires the tenant feature entitlement AND user permission AND device scope/compatibility. Hiding UI is insufficient. Tenant admins may delegate narrower firmware permissions to operators. Check authorization at submission and dispatch; revocation blocks queued/new dispatches and safely pauses rollout where supported, without claiming to cancel an already-running device flash. Preserve signed artifacts, provenance/SBOM, canary/rings, pause, compatibility checks, on-device verification and device-supported rollback. MQTT/TB sends notifications; HTTPS delivers binaries. Audit enablement, approval, rollout and outcomes.

## Vault support

OpenBao is the proposed fully open-source initial secrets backend; HashiCorp Vault remains an optional licensed provider because current releases use BSL terms. Spring Vault is a client integration for Java/Spring services, not a separate backend. Define a provider-neutral secret-reference interface with explicit provider capabilities; future AWS/Azure/GCP adapters need their own integration tests. Scope access by environment/platform, tenant, service, integration, and device. Hierarchy assignment does not implicitly grant secret access. Use workload identity, least-privilege policies, rotation/revocation and redacted audits. Do not place secret values in Git, application databases, prompts, events, logs or evidence. Browser entry uses a narrowly scoped broker/direct vault flow without persistent application storage; never expose broad vault tokens. The OpenBao/Vault choice remains proposed until compatibility and operational tests pass.

Vault Enterprise namespaces are optional and license-dependent. Non-Enterprise deployments require explicit policy/mount isolation or separate instances according to threat model; namespaces must not be assumed available. Provider failure must fail closed for privileged operations; telemetry continuity policy must be designed without relaxing tenant isolation.

## Delivery and acceptance

M1: vault abstraction/reference handling and configuration lifecycle. M2: tenant identities, permissions, entitlements, operator/device command domain. M3: authenticated device delivery, acknowledgment/replay/reconnect behavior. M4: separated console logins, Operators page and REST/gRPC/WebSocket integration. M5: entitled firmware management. M6: evidence, secret rotation/revocation and resilience validation. M8: identity/vault configuration in deployment plans. M9: final full legacy migration/cutover.

Each affected stage requires code, tests, docs, deployment artifacts, its complete relevant gate and full regression gate. Add negative tests for admin/operator token interchange, cross-tenant and unassigned-device access, excessive delegation, forbidden property updates, duplicate/stale commands, expired invitations, revocation during sessions/queues, firmware entitlement bypass, secret leakage and vault-policy isolation. Verify genuine device acknowledgments, configuration rollback and final migration reconciliation in representative isolated environments. PR/CI/human approval remains mandatory.
